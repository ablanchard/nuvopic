# ADR 0004: Typed photo filtering and visual query builder

- Status: Proposed
- Date: 2026-08-12
- Owners: NuvoPic maintainers

## Context

NuvoPic currently exposes several independent ways to filter photos:

- the search box performs a case-insensitive substring search over the generated
  description and assigned person names;
- the sidebar filters by one person, one tag, one smart tag, and a capture-date
  range;
- smart tags can match path, capture date, description, or location name;
- the photo grid, timeline, and bulk reprocessing flow each pass the current
  filter set through their own API shape.

This is easy for simple searches but cannot express queries such as:

```text
Photos from 2024 containing Alice, tagged "holiday", wider than 1920 pixels,
without a known location, and with an outdated caption model.
```

Adding one control and one query parameter per field will not scale to all
photo fields or to combinations of `AND`, `OR`, and `NOT`. A text query language
solves the expressiveness and shareability problem. Apache Lucene's classic
query syntax is a familiar reference, but full compatibility would introduce
features that are difficult to discover and unnecessary for database
filtering, including bracketed ranges, boosts, fuzzy and proximity operators,
regular expressions, and substantial escaping rules.

Lucene itself also distinguishes human-entered free-text queries from filters
whose values are generated by application controls. NuvoPic needs both: an
approachable graphical interface for ordinary use and an editable expression
for advanced use, shared links, and API clients.

Datadog's search experience is a useful interaction model. It combines
`field:value` expressions with autocomplete, facets, syntax highlighting,
inline validation, and a raw editing mode. NuvoPic can adopt these interaction
principles without copying Datadog's complete grammar or requiring a search
engine.

## Decision drivers

- A user must be able to filter without learning a query language.
- Every useful field on a photo must be available through a stable public name.
- Advanced users must be able to type, copy, paste, bookmark, and share a
  filter.
- Visual and textual editing must have exactly the same semantics.
- The photo grid, timeline, counts, and bulk actions must select the same set of
  photos.
- Field types must determine valid operators and values.
- Invalid input must produce an actionable error, never a silently broadened
  query.
- User input must never become an unvalidated SQL identifier or SQL fragment.
- The first version must work with PostgreSQL and the current application stack;
  it must not require Apache Lucene, Elasticsearch, or another service.
- Existing URLs and clients need a gradual migration path.

## Decision

NuvoPic will introduce a small, typed **NuvoPic filter expression** and a
Datadog-inspired visual query builder. It is Lucene-like where that is familiar,
but it is deliberately not Lucene-compatible.

Both editing experiences will operate on one canonical, typed abstract syntax
tree (AST). The text parser produces this AST, visual controls edit it, and a
single server-side compiler converts it into parameterized PostgreSQL
predicates.

```text
Text expression --------> parser --------+
                                         |
Visual query builder --------------------+--> typed filter AST
Sidebar facets --------------------------+         |
                                                   v
                                           validation/compiler
                                                   |
                          +------------------------+--------------------+
                          v                        v                    v
                      photo grid               timeline          bulk actions
```

The AST, rather than SQL or the user's original string, defines filter
semantics. The UI will serialize the AST to a canonical expression for URLs and
API requests. The server will parse and validate that expression again and
remain the authority on accepted fields, operators, and limits.

### Query language

The language will use these intentionally small rules:

- `field:value` performs the field's natural match. It is a
  case-insensitive contains match for text, an exact match for identifiers and
  enums, and a membership match for tags and people.
- `=`, `!=`, `<`, `<=`, `>`, and `>=` provide explicit typed comparisons where
  the field supports them.
- Adjacent clauses imply `AND`; the `AND` keyword remains accepted for clarity.
- `OR`, `NOT`, and parentheses express alternatives, negation, and grouping.
- A leading `-` is shorthand for `NOT`.
- Double quotes delimit values containing whitespace or reserved characters.
- `\"` represents a quote and `\\` represents a backslash inside a quoted
  value; other backslash escapes are rejected instead of guessed.
- An unqualified word or quoted phrase searches the default text fields.
- `has:field` tests whether a nullable or related field has a value.
- Keywords are case-insensitive, but the canonical serializer emits uppercase
  `AND`, `OR`, and `NOT`.

Operator precedence, from highest to lowest, is parentheses, `NOT`, `AND`
(including implicit adjacency), then `OR`. Public field names are
case-insensitive and serialize as lowercase `snake_case`. Values preserve their
case even when matching is case-insensitive.

Examples:

```text
sunset
person:"Alice Smith" tag:holiday
taken>=2024-01-01 taken<2025-01-01 width>=1920
(tag:holiday OR tag:weekend) NOT has:location
caption:"red bicycle" path:"family/2025"
caption_version!=5.0.0 has:faces
```

Calendar values have useful typed shorthand:

```text
taken:2024       # the 2024 calendar year
taken:2024-08    # August 2024
taken:2024-08-12 # that calendar day
```

The parser will expand these values to a half-open time interval. Expansion
uses the workspace time zone when one exists and UTC otherwise. Explicit
timestamps must use ISO 8601.

The first version will not implement Lucene's bracketed range syntax, `+`
required clauses, fuzzy search, proximity search, boosts, regular expressions,
or arbitrary wildcards. They add grammar and performance costs without helping
the primary filtering use cases. Ordinary comparisons and autocomplete are
easier to learn.

### Boolean and missing-value semantics

The language uses set-based Boolean semantics rather than exposing SQL's
three-valued `NULL` behavior:

- a positive comparison against a missing value is false;
- `field!=value` means the field exists and is not equal to the value;
- `NOT field:value` is the complement and therefore includes missing values;
- `has:field` and `NOT has:field` are the explicit existence tests;
- repeated collection clauses are independent, so `tag:beach tag:family`
  requires both tags, while `tag:beach OR tag:family` accepts either.

These rules must be documented and covered by parser-to-SQL integration tests.

### Public filter fields

Query names are an allowlisted public API, not interpolated database column
names. Friendly names decouple saved filters from future schema changes.

All scalar columns in the current `photos` table are covered. Large internal
payloads are exposed only through an existence predicate. Useful related and
derived values are also first-class fields.

| Query field | Source | Type | Initial operators | Notes |
| --- | --- | --- | --- | --- |
| `id` | `photos.id` | UUID | `:`, `=`, `!=` | Exact match; primarily diagnostic |
| `path` | `photos.s3_path` | text | `:`, `=`, `!=` | `:` is case-insensitive contains |
| `taken` | `photos.taken_at` | date/time | `:`, `=`, `!=`, `<`, `<=`, `>`, `>=`, `has` | Supports calendar shorthand |
| `date_precision` | `photos.taken_at_precision` | enum | `:`, `=`, `!=`, `has` | `exact`, `day`, `month`, `year`, `unknown` |
| `date_source` | `photos.taken_at_source` | enum | `:`, `=`, `!=`, `has` | Includes `exif`, `filename`, `path`, and `manual` |
| `latitude` | `photos.location_lat` | number | `=`, `!=`, `<`, `<=`, `>`, `>=`, `has` | Range `-90` through `90` |
| `longitude` | `photos.location_lng` | number | `=`, `!=`, `<`, `<=`, `>`, `>=`, `has` | Range `-180` through `180` |
| `location` | `photos.location_name` | text | `:`, `=`, `!=`, `has` | Friendly alias for the location name |
| `caption` | `photos.description` | text | `:`, `=`, `!=`, `has` | `description` is accepted as a compatibility alias |
| `width` | `photos.width` | integer | `=`, `!=`, `<`, `<=`, `>`, `>=`, `has` | Positive pixels |
| `height` | `photos.height` | integer | `=`, `!=`, `<`, `<=`, `>`, `>=`, `has` | Positive pixels |

| `faces_version` | `photos.faces_version` | version text | `:`, `=`, `!=`, `has` | Exact match for `:` |
| `created` | `photos.created_at` | date/time | `:`, `=`, `!=`, `<`, `<=`, `>`, `>=`, `has` | Import record creation time |

`has:location` is true when at least one of location name, latitude, or
longitude is present. `has:faces` and `has:tags` test related records.

Bare text searches `caption`, `location`, `path`, `person`, and `tag`. This is a
broader but predictable replacement for the current description-or-person
search. Searchable fields and aliases will be returned by the filter metadata
endpoint so the UI does not duplicate the allowlist.

When a later migration adds a photo column, it is not automatically exposed.
Its public name, type, operators, null behavior, indexes, and privacy impact
must first be added to this registry and tested. "All fields" therefore means
all approved fields, not unchecked access to future database columns.

### Typed AST and field registry

The implementation will define a transport-independent representation similar
to:

```ts
type FilterNode =
  | { type: "and" | "or"; children: FilterNode[] }
  | { type: "not"; child: FilterNode }
  | { type: "predicate"; field: FilterField; operator: FilterOperator; value: FilterValue }
  | { type: "exists"; field: FilterField }
  | { type: "text"; value: string };
```

A central field registry will contain, for every public field:

- display label and aliases;
- value type and valid operators;
- parsing and normalization rules;
- autocomplete or facet source;
- SQL compiler function;
- whether the value is sensitive or suitable for display.

The parser, serializer, metadata endpoint, query builder, and SQL compiler must
consume this registry or a generated client-safe subset of it. Adding a field
in only one layer is not sufficient.

### Visual query-builder experience

The default UI will be a query bar with filter chips rather than a blank raw
syntax input.

1. Selecting **Add filter**, or typing in an empty bar, opens a searchable list
   of friendly fields such as **Date taken**, **Person**, **Tag**, **Width**, and
   **Has location**.
2. Selecting a field shows only valid plain-language operators, for example
   **contains**, **is**, **is not**, **before**, **after**, **at least**, **at
   most**, **is set**, and **is not set**.
3. The value control matches the type: a date picker, number input, enum menu,
   or an autocomplete list with value counts.
4. Completed clauses render as editable chips. Adjacent chips use **and** by
   default. Users can create an **or** group and negate a chip or group.
5. The result count updates after a short debounce. A clear action removes the
   entire expression.

The bar also has an **Edit query** mode for direct text entry. It provides:

- field and value autocomplete;
- syntax highlighting;
- inline errors with the failing character range and a suggested correction;
- a short, contextual syntax reference and examples;
- conversion back to chips whenever the expression is valid.

Pasting a valid expression into the visual bar creates chips. A syntactically
valid expression that the current chip editor cannot represent remains usable
in text mode and must never be silently simplified.

Existing Person, Tag, Smart Tag, and Date sidebar controls will become facets
over the same AST. They may remain as shortcuts, but they will no longer hold a
second independent filter state. On mobile, the same builder appears in the
existing filter panel with a full-screen field/value picker.

The UI must be keyboard operable, expose meaningful accessible names for chips
and operators, and not rely on color alone for syntax or errors.

### Facets and autocomplete

The API will expose field metadata and typed value suggestions rather than let
the client infer schema details:

```text
GET /api/v1/photos/filter-metadata
GET /api/v1/photos/filter-values?field=person&prefix=ali&filter=...
```

Suggestions for finite or related fields include result counts. When computing
facet counts, the service should evaluate the current expression without the
clause being edited so a user can discover alternatives that would otherwise
have a zero count. Free-text suggestions are not required in the first phase.

Endpoints will cap the number of returned values, debounce requests, and avoid
returning the `placeholder` payload or other internal values.

### API and URL contract

The canonical text expression is sent as a UTF-8 `filter` query parameter:

```text
GET /api/v1/photos?filter=person%3A%22Alice%20Smith%22%20width%3E%3D1920
GET /api/v1/photos/timeline?filter=...
```

Bulk actions accept the same expression in the request body. The current `q`,
`tag`, `person`, `smartTag`, `from`, `to`, and `dateUnknown` inputs remain
temporarily supported and are converted to AST nodes. If `filter` and legacy
inputs are both present, they are combined with `AND`. Responses may include
the canonical expression so clients can normalize saved URLs.

Invalid expressions return `400` with a stable error shape:

```json
{
  "error": "invalid_filter",
  "message": "Width expects an integer",
  "start": 7,
  "end": 13,
  "expected": "integer"
}
```

The UI stores the canonical expression in the page URL so filters are
bookmarkable and survive reloads. It uses history replacement while editing
and creates a history entry when a filter is committed.

The initial limits are 2,000 input characters, 50 predicates, nesting depth 8,
and 20 alternatives in any one `OR` group. Exceeding a limit returns a specific
validation error. Limits may be tuned from observed query cost.

### PostgreSQL compilation and performance

NuvoPic will implement a small parser and compiler in TypeScript. It will not
add a Lucene runtime. The compiler will:

- resolve fields only through the allowlisted registry;
- convert values to their declared types before querying;
- generate SQL exclusively from reviewed templates;
- bind every user value as a PostgreSQL parameter;
- use `EXISTS` subqueries for tags and people;
- compile all photo-selection consumers through the same function;
- reject unsupported operator/field combinations before executing SQL.

Initial indexing work will include B-tree indexes for commonly compared date,
numeric, enum, and version fields, plus the existing relationship indexes.
Case-insensitive contains matching on caption, location, and path will be
benchmarked with realistic libraries. If sequential scans become material,
NuvoPic will add `pg_trgm` GIN indexes and minimum substring lengths rather than
introduce a separate search service prematurely.

The first release remains a Boolean filter and keeps the existing deterministic
photo ordering. Relevance ranking, stemming, accent folding, semantic search,
and image similarity are separate decisions.

### Saved smart tags

Smart tags and interactive filters will converge on the same expression model.
A later migration will add an expression or versioned AST to each smart tag and
translate the current `field`, `values`, and `rule` records. Until that
migration, selecting a smart tag inserts an equivalent AST subtree.

ADR 0003 uses this same user-facing abstraction for detected events instead of
adding albums. An automatic event smart tag evaluates an internal
`event:<stable-id>` predicate backed by materialized detector membership. This
predicate is generated by NuvoPic rather than accepted as an arbitrary public
field in the first release. It still compiles through the common AST and
photo-selection path, so grids, timelines, counts, and bulk actions see the
same set. User-query smart tags remain dynamic predicates; event smart tags add
and remove backing membership only through the versioned event detector and
recorded user constraints.

Persisted filters will record a language version. The server will retain field
aliases and provide migrations when semantics change; it must not reinterpret
an old saved filter silently.

## Consequences

### Positive

- Most users can filter through discoverable fields, operators, and values
  without memorizing syntax.
- Power users retain fast keyboard entry and shareable, readable expressions.
- One AST eliminates semantic drift between the grid, timeline, facets, smart
  tags, and bulk actions.
- Typed operators make number and date filters simpler than Lucene range
  notation.
- The allowlisted compiler keeps SQL generation safe and makes field behavior
  testable.
- PostgreSQL remains sufficient for the current filter workload.
- The field registry provides an explicit process for exposing future photo
  metadata.

### Negative

- Maintaining synchronized text and visual representations is more work than a
  conventional search box.
- Boolean group editing is a substantial interaction and accessibility task.
- Facet counts can add database load and require caching or query tuning.
- This familiar-looking syntax will differ from Lucene and Datadog at the
  edges, so the UI and documentation must call it NuvoPic syntax.
- Canonical serialization and language versioning become long-lived API
  responsibilities.

### Risks and mitigations

- **Users assume full Lucene support:** describe the language as Lucene-like,
  reject unsupported operators clearly, and link to NuvoPic's own short
  reference rather than Lucene documentation.
- **A visual edit changes Boolean meaning:** always edit the AST, display group
  boundaries, test round trips (`text -> AST -> text -> AST`), and preserve
  text-only expressions.
- **Expensive contains or large-`OR` queries:** enforce structural limits,
  measure query plans, add targeted indexes, and cap facet cardinality.
- **SQL injection through field names:** map public fields to closed compiler
  functions; never concatenate an input field or operator.
- **Saved filters break after schema changes:** use stable aliases, language
  versions, and explicit migrations.
- **Facet counts leak internal values:** expose only approved display values and
  never facet internal payload fields.

## Alternatives considered

### Implement the full Apache Lucene query syntax

Rejected. It is expressive but includes search-engine concepts that do not map
cleanly to typed PostgreSQL fields or a visual filter builder. It would make the
common date and numeric cases harder to remember and could create a false
compatibility promise. Running Lucene or Elasticsearch solely for parsing and
filtering would also add unnecessary operational complexity.

### Use Lucene's simple query parser

Rejected as the public contract. It is forgiving for free text but can ignore
syntax errors and produce unexpected results. Silent recovery is inappropriate
for filters that may drive bulk reprocessing. NuvoPic will instead report
precise errors and preserve the last valid result set while the user edits.

### Provide only a visual query builder

Rejected because filters would be slower for expert users and harder to share,
document, paste, version, or use through the API. The canonical textual form is
also a useful debugging boundary.

### Keep adding dedicated controls and query parameters

Rejected because the number of controls grows with every field and cannot
represent arbitrary Boolean grouping. Existing controls remain useful only as
facets backed by the common AST.

### Accept SQL, JSON operators, RSQL, or FIQL

Rejected for the user-facing syntax. SQL is unsafe and exposes storage details;
generic API grammars are precise but less approachable than autocomplete-backed
`field:value` expressions. A structured JSON AST may be added for trusted API
clients later, but it will use the same validation and semantics.

### Translate natural language into filters

Deferred. Natural language can be a convenient optional assistant, but it is
not sufficiently deterministic to be the saved or executable representation.
Any future translation must show the resulting AST for confirmation before it
can trigger a bulk action.

## Implementation outline

This ADR does not authorize or include implementation. The intended sequence is:

1. Define the field registry, AST, grammar, canonical serializer, validation
   errors, and language-version policy.
2. Implement parser and serializer unit tests, including property-based round
   trips, quoting, precedence, missing values, date shorthand, and complexity
   limits.
3. Implement the parameterized PostgreSQL compiler and integration tests for
   every field/operator pair and Boolean combination.
4. Route photo listing, timeline, counts, and filtered bulk reprocessing through
   the same compiled predicate.
5. Add `filter` to the API while translating and retaining the legacy inputs.
6. Add filter metadata and value-suggestion endpoints with query-cost limits.
7. Build text mode with autocomplete, validation, URL synchronization, and an
   accessible short reference.
8. Build the chip-based visual editor and connect existing sidebar facets to
   the same AST.
9. Migrate smart tags to versioned expressions after compatibility and query
   performance have been observed in production.
10. Deprecate legacy filter parameters only after published client migration
    guidance and at least one compatibility release.

## Acceptance criteria

- Every field in the table above can be filtered with all declared operators.
- The same canonical filter yields the same photo IDs for the grid, timeline,
  facet counts, and bulk-action preview.
- Parsing and serialization preserve Boolean meaning and typed values.
- Invalid fields, operators, values, and over-complex expressions fail with a
  positional `400` error and execute no query.
- No compiler path places user-controlled field names, operators, or values
  directly into SQL.
- A keyboard-only user can create, edit, group, negate, and remove filters.
- A valid filter can round-trip through the URL and a page reload.
- Existing filter URLs retain their current behavior during the compatibility
  period.
- Query plans for agreed representative libraries and filters meet the response
  time budget before release.

## Open questions

- What is the product response-time budget and representative maximum library
  size for filter and facet benchmarks?
- Should bare text retain only the current caption/person scope for strict
  compatibility, or adopt the broader default-field set immediately?
- When a workspace time zone is added or changed, should saved calendar filters
  retain their original zone or follow the workspace?
- Should saved filters remain the existing smart-tag feature, or should NuvoPic
  distinguish dynamic smart tags from named saved views?
- Is a structured JSON AST needed as a public API in the first release, or is
  the canonical text expression sufficient?
